# Architecture

## 1. 설계 원칙
- 기능을 데이터 탐색, 전처리, 분석, 시각화, 리포트 생성으로 분리한다.
- 각 단계는 독립적으로 실행 가능해야 한다.
- 분석 로직과 결과 렌더링 로직을 분리한다.
- 데이터 처리 과정과 생성 결과를 로그로 추적할 수 있어야 한다.

## 2. 권장 기술 구조
현재 저장소에는 구현 코드가 없으므로, 아래 구조를 기준 설계로 제안한다.

- Backend: Python 기반 데이터 처리 파이프라인
- Frontend: 결과 확인 및 리포트 다운로드용 UI
- Data layer: 파일 업로드, 임시 저장, 결과 파일 관리
- Report layer: Markdown 및 HTML 생성

## 4. 모듈별 역할

### 4.1 `api`
- 파일 업로드, 분석 실행, 결과 조회를 위한 엔드포인트를 제공한다.
- 작업 상태와 오류 메시지를 반환한다.

### 4.2 `services`
- 분석 파이프라인의 오케스트레이션을 담당한다.
- 탐색, 전처리, EDA, 시각화, 리포트 생성을 순차적으로 연결한다.

### 4.3 `analyzers`
- 기본 개요, 데이터 품질 진단, 통계 요약, 그룹 분석 로직을 담당한다.

### 4.4 `preprocessors`
- 결측치 처리, 형변환, 중복 제거, 이상치 처리, 범주 정리 등의 로직을 관리한다.
- 전처리 계획과 실제 실행 코드를 분리해 관리한다.

### 4.5 `visualizers`
- 그래프 종류 추천과 이미지 생성 로직을 담당한다.
- 시각화 결과의 저장 경로와 메타데이터를 관리한다.

### 4.6 `reporters`
- Markdown, HTML, 이미지가 포함된 최종 리포트를 생성한다.
- 요약 정보와 인사이트를 통합한다.

### 4.7 `utils`
- 파일 경로, 공통 로깅, 예외 처리, 설정 로딩 등을 처리한다.

## 5. 처리 흐름
1. 사용자가 데이터 파일을 업로드한다.
2. 시스템이 데이터 형식과 컬럼 구조를 확인한다.
3. 데이터 탐색 결과를 생성한다.
4. 전처리 필요 여부를 진단하고 계획을 만든다.
5. 전처리를 실행하고 정제 데이터를 만든다.
6. EDA와 시각화를 실행한다.
7. 인사이트를 정리한 리포트를 생성한다.
8. 사용자는 HTML 또는 파일 형태로 결과를 확인한다.

## 6. 데이터 처리 기준
- 입력 파일은 CSV, Excel, Parquet 등 범용 형식을 우선 지원한다.
- 결측치와 이상치 처리 기준은 설정값으로 제어 가능해야 한다.
- 전처리 결과는 원본과 분리해 저장한다.
- 모든 처리 단계는 재실행 가능해야 한다.

## 7. 확장 포인트
- 자동 모델링 단계 추가
- 텍스트 데이터 분석 추가
- 시계열 분석 추가
- 대시보드형 UI 추가
- 보고서 템플릿 분기 추가

## 8. 운영 고려사항
- 대용량 데이터 처리 시 샘플링 전략이 필요하다.
- 분석 실패 시 중간 결과를 유지하고 재시도할 수 있어야 한다.
- 로그, 캐시, 결과 파일 정리 정책이 필요하다.
